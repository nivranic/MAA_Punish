# 共享作战启动守卫 C 实施计划

**Goal:** 每次共享「作战开始」尝试最多一个物理点击：两种明确的阻塞提示快速收束，没有确认进展则不再点，正常交回模式原有父链。这不是跨同一战斗的总额锁；例如 R02 已进入角色详情、原父链明确返回准备页后，是新一次尝试。

**Architecture:** 保持公开入口识别；同帧重新定位原生点击节点，用原生候选等待观测下一屏。失败时用任务内限定的既有 App 失败标记结束当前任务，不调用会返回、暂停或确认弹窗的通用清理动作。各模式原有选人、首发位、队长、体力与结算逻辑仍由自己负责。

**Tech Stack:** MaaFramework 5.14.2 Pipeline、Python CustomAction、Android App 任务历史、pytest/native Controller。

## 1. 合成及真帧先立回归

- 新建 `agent/tests/test_shared_combat_start_native.py`；加载实际资源及历战任务覆盖。用合成分阶段画面和原生 Controller 验证①按钮迁移点击新区域；②过期按钮不点；③两种阻塞快收；④短时无变化仍等待，支持约 9 秒才进展（旧现场时间包含盲等待，不是首帧基准）；⑤保持原页或未知到期不重试；⑥可识别弹窗由原有 owner 处理；⑦慢载入、直接进 HUD、出现一帧载入后回原页；⑧两场连续各一击及 20/60 次跨场实点上限。不拿纯 mock 结果替代原生识别、实际 `JumpBack` 或任务历史；原始手机帧只放忽略的 `debug/`，另做私有的真帧 OCR 回放。
- 对照现有资源，先跑应失败的用例：旧 click 复用旧坐标且没有当场的证据等待；禁止仅以静态字段或时间睡眠代替行为断言。运行：隔离工作目录下 `python -m pytest -c <repo>/agent/pytest.ini -p no:cacheprovider --basetemp <debug>/tmp -q <repo>/agent/tests/test_shared_combat_start_native.py`。另验证手动停止、原生 Click 失败、已达上限均不能点击第二次。

## 2. 共享原语与真实失败历史

- 在 `resource/base/pipeline/War_Zone.jsonc` 内保留 `作战开始.recognition` 和前置队长分支。`点击作战开始` 同帧重认原 OCR 与底色，`box_index=0` 定位并使用 `target:true`，保留 60 及历战 20 的 `max_hit`。允许选中点击节点前识别出已经加载／HUD／下载，不用旧框补点，不把有文字而缺白底的下载背景视为按钮。
- 阻塞 OCR 只用国服实拍校准的 `[535,336,210,40]` 与 `^队长不能为空$`／`^首发位不能为空$`，不凭字面编其他语言变体。生产等待从 12 秒候选验证开始：这是有依据的首版预算，不是设备 SLA；另给交接确认有限时间。交接要求现有载入/HUD/弹窗等有证据的后继；无 Start 但无稳定后继不算成功。同帧或单帧互相矛盾的证据不得导致又一次点击。若遇短载入后回原页，确认分支的计时结束仍当同一次，不能回流重试。
- 在 `agent/action/basics/combat_start_failure.py` 与 `agent/agent_file.py` 增加很小的 CustomAction：利用 `Context.override_next("任务失败优雅退出", ["停止任务"])`，仅对本次任务、仅在明确要失败时生效。动作成功后必须走准确的既有失败标记再 `StopTask`，不改共享资源、App、长期缓存，不调用 `run_task` 或任何控制器输入；若改写失败则不调用旧清理路径。验证原先有过已恢复超时仍能被 App 分类，后续任务的共享收尾不被覆盖；用 Android 历史分类逻辑与原生记录交叉核对，不把 native Succeeded 当业务成功。
- 不启用任何会使生产失败吞没成业务成功、或遇未知时导航的方案。专门回归取消和目标被别的界面抢占。

## 3. 受影响消费者和离线验收

- 单查 D04 `作战界面`、D07 `进入战区选人界面` 的真实父链，确认原 owner 接到加载/HUD/弹窗，不向 Guard 借用任务 readiness。D06 用 `囚笼作战程序` 真分支回归；次数/耐力等已有后继若会紧跟 Start，只在 D06 加纯识别交接，不把该条件全局启用。R01 区分共享点击与固定坐标旁路；R02/R04 复核自己的战斗列表，只有经真实或原生回归可证与 Start 直接相邻的结算、弹窗或模式后继才通过任务内覆盖接回；R03 启动独立，须验证旁路不变。
- D08 分别验证 `开始挑战` 下的旧完整父链、`日常断点_历战映射` 的直接准备页入口、`成员整备` 入口，保持 20 cap 与已有前置返回。若后两入口不接 HUD/弹窗/结算，先在 D08 闭合**仅从 D08 已识别准备链出发**的 owner；不能给日常入口无条件接任何任务遗留的通用 HUD。加否定例：在其它玩法的 HUD 上直接打开 D08 不启动回调。修改前把具体复现固定成原生测试。
- 自动主线与战斗辅助通过 `[JumpBack]未选人` 亦间接消费；验证现有体力等模式交接，不改变独立 `_速通` 或手动拟战场域的只识别入口。各模式若在补测中出现新事实，只处理与这段交接直接相关的路径，不修改通用编队规则。
- 运行四语言 bundle 加载、Schema、interface/tasks 校验和相关定向测试。查看原生轨迹里的实际 click、后继及历史；确认 R03 本地补丁和 R02 已有识别未被这轮回退。先明确本地验证结果和剩余边界；部署以及设备正常验证单独授权。禁止为采样弃档、买体力、刷新或强制败北。

## 本地实施与剩余边界

- 2026-11-25：共享管线及任务内收尾已接入；实际资源定向 165 项通过，加强后的 D08 成员整备、R01／R04 与次数回归 9 项通过；国服十张原帧零输入回放通过。base、繁中、日文、英文、桌面 Win32、PlayCover 资源各自加载，资源及选项 Schema 通过。接入后的独立全量 4222 通过／238 跳过。其后复审只在 D08 成员整备加原清队识别的确认：零战斗时长的战前地图能命中「结算」，不能视为战斗后状态；只等旧页消失并看到已知编队迹象，不变更原始点按和结算逻辑。该尾差异用残留帧／吞点红绿例、真帧回放和定向回归验证。
- 一个尝试从共享点击开始，到原生双采样确认的交接结束。等待过程无第二击；只出现一次载入后回准备页不得重新点击。若两个采样都已确认推进，随后更晚又回到准备页，处理权已在原有父链，不把这当成全局战斗身份锁；后续如有日志证明回流连点，再按模式校准，不引入共享的跨场状态。
- R02 角色详情目前只对国服日志里的「编入队伍＋战斗参数」确证。现有繁中／日文详情处理能识别各自文案，但新守卫在旧父链之前执行，未命中上述简中双锚时会安全停下，**不是**保持了这些分支的详情恢复。已装备时的「卸下」也是旧父链可识别且新守卫未承诺的分支。需要该语言、该布局的成对证据再补两锚，不能把加载通过当作恢复通过。
- D08 `成员整备` 已就地成为清队/选人链的拥有者，日常入口不会吸收无来由的 HUD。旧的冷编队直达候选仍缺模式身份锚及本地承接，保留作为单列缺口，不扩大本次变更。战斗辅助「自动检测」与「持续战斗」有不同候选列表；前者纯 HUD/下载弹窗的归属仍需独立校验。本地测试或双帧状态机都不能代替实际 Android 队列的 App 业务失败分类及恢复。

## 等待授权的真机验收

- 先限定国服、已确认模式和一次正常入场；仅同步必要的同版 Agent 与任务/流水线文件到已核实的直达路径，逐一复读目标字节哈希，检查没有多出的同名嵌套目录。不顺带部署 R03 或改动黑罩、最低亮度、防锁设置。
