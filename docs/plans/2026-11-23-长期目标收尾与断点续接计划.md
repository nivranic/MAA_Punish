## [S1] Problem

### S1.1 长期任务链路与伞形验收基线

初始目标出自《MAA_Punish_iQOO16_最终优化方案》（2026-10-23 基准）：**20 个日常实例（D01-D20）＋6 套肉鸽（R01-R06）＋逆冕专项策略（以露西亚·逆冕为第一优先级：单体/多波/长期补资源/停止、默认无意外切人）＋日志清理与知识沉淀**，并以 7.6「专项完成检查表」为「专项验收完成」的硬标准（业务终态须正向证据；按钮名/节点名/StopTask 成功不能单独证明通关；`PASS + defeat` 不计通关）。

此前选择 R03 和 R01 作为两个优先验收切片，均属于伞形必验项。**2026-11-25 复核：两项正式终局仍待验。** R03 的 seg126 有真实统计但漏停并再次启程；seg207 的抽样及结束前后第一章画面不支持整局结案。R01 已证续旧档和同回调识别败北退出，最新 60 次启动封顶记录为有效失败，并非「剧幕高潮→收场→重开」。单独的接手任务完成不代表 7.6 验收完成；此处不存当前 goal 激活状态或设备部署版本，真机验证另行授权后读回实装。

伞形剩余项（不阻塞两阶段，登记于 S2.4 路线图）：日常 D01-D20 分支验收矩阵收尾、R02/R04/R05/R06 必验流程缺口（含 R06 三模式与真实耗尽）、逆冕多波/长期补资源/停止与囚笼 Boss 实际计分、启动阻塞根因、外语/桌面验证、日志清理与 7.6 检查表收尾。

### S1.2 交接提示词审查

旧草案沿用了 seg207 结案及当时的 goal／设备状态，不再作为独立交接。修订版见 S2.3：交接须分开列历史实证、代码或离线证据、真机未验、当前授权；不以历史部署哈希、输赢或随机性推定某个新问题的根因。

### S1.3 断点续接缺口

用户需求：日常任务打到一半退出游戏/MAA 后，重新跑日常必须**从断点继续，不能从头开始**；日常断点有效性仅限**当日 05:00 至次日 05:00**（游戏每日 5 点刷新）；非周期任务（肉鸽流程等）按具体情况另行分析。

现状缺口：

- preset_daily 20 实例（19 启用，D09 默认关）中途失败/被杀后重跑，从第一个任务重新执行全链导航，已完实例重复空跑（耗时），次数/体力类实例存在重复消费风险（仅靠各任务内既有幂等检查兜底，粒度与覆盖不一）；
- 无「同一游戏日内已完成实例」的统一账本；跨 05:00 的归属语义无统一实现（仅角色缓存/矩阵扫描 memo 有游戏日键先例）；
- 肉鸽各模式已有各自的存档续跑行为（R03 已定型契约、R01 重开即续），但没有统一的「断点=什么、恢复=什么行为」契约文档，中断恢复靠零散实证支撑。

### S2.1 日常断点续接契约（05:00 游戏日账本）

**状态层**：`daily_progress.json`，存项目根（与 `role_cache.json` 同目录约定，`role_cache_policy.cache_path` 同款解析）。格式：

```json
{
  "version": 1,
  "entries": {
    "领取体力": {"game_day": "2026-11-23", "result": "done", "updated_at": "2026-11-23T06:12:03+08:00"},
    "购买物品/逆元碎片-普通商店": {"game_day": "2026-11-23", "result": "done", "updated_at": "..."}
  }
}
```

**游戏日语义**：`game_day = (now - refresh_hour=5h)` 的日期；00:00-05:00 归属前一天（与 `_R3_SCAN_MEMO`/周缓存冻结时钟测试同语义，复用 `role_cache_policy` 的时刻规整工具）。断点有效性窗口=同一 game_day 内；跨 05:00 后旧条目自然失效、全量重跑——即用户「当日 5 点至次日 5 点」规则。

**键（key）**：任务实例标识。单实例任务=任务名（如 `领取体力`）；购买物品三实例=`购买物品/逆元碎片-普通商店`、`购买物品/涂装设计草稿-宿舍商店`、`购买物品/武器设计草稿-宿舍商店`（经 `选择物品` case 的 pipeline_override 注入 `attach.daily_progress_key`，沿用 D14 案例给 `购买_宿舍.attach` 注参的既有模式）。

**准入与写账（2026-11-25 修订）**：

1. 各原任务入口先执行共享 `日常账本准入`，用入口 `attach.daily_progress_guard_node` 找到原工作守卫。`DailyProgressAdmit` 区分有效 v1、文件不存在、不可用；只有 `FileNotFoundError` 视为空账本。坏编码、坏 JSON、不可读、重复字段、不受支持的状态等使原生任务失败，不点击、不跳过、不修改文件；显式重置也不掩盖损坏。
2. 只有同键同日的肯定 `done` 可进入 `空任务`。待办将 task ID、入口、实例键和准入游戏日写入任务内 `Context` 并读回，工作守卫 `DailyProgressCheck` 核对后进入原候选。角色、动作和导航不由账本改写。同一任务回到入口不刷新日期。
3. `DailyProgressMark` 仅在原业务成功尾使用；凭证不匹配、观察到跨 05:00、停止或写失败，写入省略且保留原工作收尾。使用同目录唯一临时文件、刷盘并在原子替换前再检查日期和停止。保持 v1 和实例键，`updated_at` 仅供审计。不把宿舍中途态或其它 NO-MARK 改成已完成。

**为什么不用 Tasker 事件打标（重要语义）**：`TaskerEventSink` 的 `Succeeded` 是原生状态——优雅退出借 `on_error` 清理链也能以「成功」终结任务（11-15 批「界面完成日志改用 TaskFinished 有效结果，避免原生成功先显示绿色」同一教训）。`done` 必须是业务成功信号，因此 mark 只认业务成功尾节点，不认 sink 事件。

**豁免**：D01 进入游戏、D20 结束游戏不挂守卫（基础设施，每次必跑；跳过 D01 会导致游戏未启动）。D09 挂守卫（默认关，无行为差异）。

**实例内部分进度**（囚笼房间/次数、历战次数、拟战场域体力等）不属本账本：沿用各任务内既有状态检查（零分/历史记录/可用次数/体力）做任务内续跑；账本只解决「整实例跳过」。二者叠加即：已完成实例秒级跳过，进行中实例进任务后由既有逻辑续进度。

**同日第二跑**：只跳过有本日 `done` 证据的实例；未落账、NO-MARK 与基础设施按各自入口逻辑运行。显式 `重置日常断点` 可清空有效账本；不可用的账本应先保留文件、检查权限或由用户恢复可读副本，不把删除当作自动恢复。

**业务边界**：05:00 前已完成且已落账的实例归旧日。若业务发生在旧日、回调发生在新日，或中间只知道检测结果、不知道实际消费日，均不补记任一天。未落账不代表没有买到或没有用药，不保证跨进程重跑去重；此时先按游戏流水人工核对，不自动重试。日内后到的奖励以游戏页面为准，账本不承担自动补领。

### S2.2 非周期任务（肉鸽）续接契约——逐模式分析

统一原则：**断点真源=游戏侧存档/进度**；无时间窗（每日限量子资源除外）；恢复=任务入口检测存档→继续，**不新起局、不毁档**（沿用 R03「存档恢复不点终止」既有契约）；存档不可读/损毁→明确失败，不自动覆盖开局（覆盖存档需用户授权，既有授权边界不变）。

| 模式 | 断点真源 | 恢复行为 | 每日限量子资源 | 现状与缺口 |
| --- | --- | --- | --- | --- |
| R01 宣叙妄响 | 剧幕进度（游戏侧存档） | 重开任务续当前剧幕，不回入门重开 | 招募刷新次数（耗尽=日耗尽终局，已实证） | 「重开任务即续」已实证（移交提示词-20261123）；缺口=未完待续路径第三场战败验证、收场终局窗口（属 /goal 阶段②，不在本特性内实现） |
