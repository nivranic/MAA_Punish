# 开发与验证指南

本文是 [AGENTS.md](../AGENTS.md) 的按需参考：接任务时先读入口，再读取与改动有关的章节。稳定命令和项目知识在此维护；本次环境实测见 [2026-10-20 验收记录](AgentHarness验收-20261020.md)，其结果不代表未来提交或其他设备已验收。

## 1. 项目地图与事实来源

MAA_Punish 是由启动器加载的《战双帕弥什》自动化资源与 Python agent。业务包括日常领取、宿舍、商店、配队与角色扫描、战区/囚笼/围剿、肉鸽和自动战斗；具体可选任务以 [interface.json](../interface.json) 导入的 [tasks](../tasks/) 与 [options](../options/) 为准，产品功能概览见 [README](../README.md)。

| 层次与目录 | 职责、消费者与修改位置 |
|---|---|

## 2. 关键运行链路与共享状态

### 启动、配置与资源

```text
启动器读取 interface.json
  ├─ import tasks/、options/；解析 i18n 文案
  ├─ 选择资源组：base + 所选语言覆盖
  ├─ 根据控制器 attach_resource_path 追加平台覆盖
  └─ 启动 agent/main.py，并提供 AgentServer socket 标识
       └─ Pipeline entry → 内置识别/动作或已注册 Python Custom
```

`agent/main.py` 初始化 Toolkit、调用 `validate_role_actions()`，随后启动、等待并关闭 AgentServer。当前调用未检查该校验的布尔返回值，因此日志报错不能视为阻止了 agent 启动；配置检查需看明确的测试结果。直接运行 `agent/main.py` 不是完整本地启动方式，缺少启动器的资源、控制器与通信上下文。

任务、语言和控制器共同决定最终节点。改 base 节点时检查对应平台和语言的同名覆盖；改 `default_pipeline.json` 时考虑所有消费者。源码检索可先用：

```powershell
rg -n '目标节点或注册名' interface.json tasks options resource agent i18n
```

### 角色缓存与布局

- [CacheRole.py](../agent/recognition/exclusives/CacheRole.py) 读取全局缓存选项；[role_cache_policy.py](../agent/action/basics/role_cache_policy.py) 定义策略来源，优先级为节点 attach、Custom 参数、已有缓存、默认值。日切依赖本机本地时间，修改语义时同时检查刷新与使用两条路径。
- 选项通过同名节点的 `attach` 合并。将多个选项改为覆盖同一个 JSON 字符串 `custom_recognition_param` 会整体替换，使另一个选项丢失；对应回归在 [test_cache_option_channel.py](../agent/tests/test_cache_option_channel.py)。
- [RoleSelection.py](../agent/action/basics/RoleSelection.py) 扫描时响应 `tasker.stopping`；中止或零结果不能更新角色缓存及刷新时间。保存入口也拒绝空结果。读取策略与写入完整性要分别验证，不能用“返回成功”代替检查旧缓存是否保留。
- [InterfaceZone](../agent/action/basics/InterfaceZone/) 按控制器处理按钮布局缓存，运行文件包括 `debug/adb_zone_offset.json`、`debug/win32_zone_offset.json`。加载器同时校准识别 ROI 和固定触屏动作（点击、长按、触点及滑动两端）；识别结果目标不重复偏移，键盘动作不添加触屏偏移，重复加载不累加。修改识别坐标前先区分原始截图、框架缩放后的画面和缓存偏移。`combat_roi_zone_map.json` 由 [gen_combat_roi_zone_map.py](../tools/gen_combat_roi_zone_map.py) 生成；变更其来源或生成逻辑后检查 diff，不把运行缓存当作共享默认资源提交。


显式 HUD 校准沿用同一 `debug/<controller>_zone_offset.json`，以 `hud_roi_calibration` 保存；不另建运行缓存。由 [`LoadROIZone`](../agent/action/basics/InterfaceZone/LoadRoiZone.py) 的显式 `from_screen=true` 参数提交，只允许“检查血量”和“检查逆冕能量空”两个节点，并绑定控制器、画面尺寸及八区几何指纹；缺失、坏型或绑定不符时，专项加载拒绝。重采八区而未提供新 HUD 时，仅在原绑定仍一致时保留旧块；布局变化使其失效，需要重新校准。`source_frame_sha256` 只记录来源，不证明 HUD 语义或技能状态；字段校验见 [hud_roi_calibration.py](../agent/action/basics/InterfaceZone/hud_roi_calibration.py)。

保存链先确认当前截图 Job 成功且图像有效；识别框接受真实 SDK `Rect` 以及 list/tuple，转换为四个严格整数后检查画面边界。全部区域和显式 HUD 参数有效才写同目录临时文件并原子替换；截图失败、中止、坏校准或写入失败保留原缓存。普通加载只应用八区，HUD 由[专项入口](自动战斗框架开发指南.md#44-受保护阶段与后续站场合同)显式要求并读回。维护时检查 [HUD 校准回归](../agent/tests/test_hud_roi_calibration.py)、[缓存回归](../agent/tests/test_roi_zone_cache.py)和[专项入口回归](../agent/tests/test_inverse_crown_layout.py)；离线通过不能替代手机保存、重启加载及实际 Context 验收。

### 自动战斗

`CombatRunner` → `CombatTask.combat_once()` → 队伍识别与角色工厂 → `BaseRole.perform()` → 角色 `do_perform()` → `CombatActions`。新增角色遵循 [战斗指南](自动战斗框架开发指南.md)，不复制另一套 Custom 注册流程。

需要修改公共状态时，先读 [session.py](../agent/action/combat/core/session.py)、[provider.py](../agent/action/combat/core/provider.py)、[role.py](../agent/action/combat/core/role.py) 与 [switch.py](../agent/action/combat/core/switch.py)：

- 非切人阶段会刷新站场角色，不能将其缩减为只在 idle 时刷新。
- R/B/Y 色位和 `cls_name` 是队伍与角色配置的共同数据。已有专属名单按名单构建；没有名单或全部是 `GeneralFight` 时，还会根据 B/Y QTE 推断人数，不能把旧注释中的“无名单即单人”当成当前行为。
- 退出判断包含覆盖界面、血量为零计时、战斗 UI、战斗外界面以及 UI 丢失；血量已确认归零后，后续未知帧不会直接抹掉计时。变更需保留 [test_session_hp.py](../agent/tests/test_session_hp.py) 等对应语义，不固定抄写当前阈值。
- `combat_once()` 在 `finally` 中调用 `combat_end()` 清理队伍、角色、帧和计时状态；长循环需响应停止。跨回合状态不应绕过会话生命周期自行长期保留。
- [runner.py](../agent/action/combat/entry/runner.py) 在正常返回后统一给出 `success=True`，其中可能包含未能进入战斗的超时路径。这是当前行为与验收风险，不能据此断言关卡已完成。
- `active_delay` 使用秒，Pipeline 的 `duration`、`interval` 等通常使用毫秒。新增调用核对具体 API，避免仅凭数值大小猜单位。

### 逆冕本场档案选项

[战斗辅助](../tasks/战斗辅助.json) 已接入 [inverse_crown_profile 共享选项](../options/inverse_crown_profile.json)，父开关“逆冕站场专项”默认 No，并位于该任务 `option` 末尾。Yes 默认仍以唯一普通边 `next=["战斗中"]` 接管HUD，不使用 JumpBack；5000ms 仅是启动识别预算，不是战斗或输入时限。子项“逆冕本场档案”一次发送完整五字段到“战斗中”和“逆冕准备页开始”的 `attach.inverse_crown_profile`：`enabled`、`scene`、`source`、`rank`、`signature_weapon_confirmed`，两个实际消费者保持一致。随后“逆冕开始方式”只选择入口，不改档案。字符串枚举按选项的英文值输入，bool 仅接受 `true`／`false`；No 向两消费者写完整关闭／unknown 档案，不消费旧 child，不重开兄弟选项的 `enabled`，后续任务不继承本次覆盖。

默认“接管当前战斗”跳过原外围选人、开战、剧情与补体力分支，绝不因缺HUD而自动开战或重开。显式“从作战准备页开始”只走新准备页节点：复用当前语言的“作战开始”OCR与背景颜色And，现有入口布局及session的 `ensure_strategy_ready` 门先于任何Start输入；角色perform门仍关闭，位于后续角色调用链；未来门解除后，同一 `CombatRunner` 调用仍须用一张新图排除HUD／重启页并确认准备按钮，至多请求一次原生Click，再由既有纯观察链核新HUD、实际逆冕身份和严格正HP。本路径目前只接受single／self／本场已确认专武；未扩大原战区或速通任务的专项支持。

[`FreshEntryCandidate`](../agent/action/combat/core/fresh_entry.py) 仅留在本次 `CombatTask`：Click成功先形成候选，不等于已入场。完成连续入场与身份绑定后，首次prepare可将孤航首发规则用于本场初始“无待结算义务／特殊球已激活”的机理推定，快照及日志明确标记 `initial_basis=same_call_entry_rule_inference`，不冒充图像观察。首次消费输入请求前、reset、停止、异常、几何读取不支持／返回None、HUD丢失或已检查归属失配及会话收尾会退役；该检查不直接比较native Controller／Resource身份或原子探测所有重载，继续依赖既有维护互斥；不持久化fresh、不以旧TaskDetail或新generation补事实，不产生后续相／长普末段／终结信号。两处 `strategy_not_ready` 原守卫仍关闭。本批实际App新选项编译28项及原序导出到native接链已获[独立接受](../build-debug/iqoo16-fresh-entry-implementation-20261026/review/report.md)，见[台账2.81](iQOO16专项实施与验收-20261023.md#281-scope14准备scope15失败与fresh-entry离线接受)；可见UI、真实Android准备页→首HUD链、750ms帧龄可达性和策略验收仍需另验，离线接受不等于设备输入已获验收。

[`InverseCrownProfile.from_node_data`](../agent/action/combat/config/inverse_crown_profile.py) 仅接受成功读取的 dict。固定 SDK 节点查询返回 None、坏类型时走 `profile_invalid` 拒绝，不能默认为普通战斗；合法 `{}`、有效节点未设置 profile、空 attach 和显式 No 继续兼容普通模式。修改选项须同时检查真实 App 编译数组、同 Tasker 覆盖隔离与消费者读取；[合同测试](../agent/tests/test_inverse_crown_task_option.py)及[可选实际 App 接链测试](../agent/tests/test_inverse_crown_app_plan_integration.py)不替代渲染 UI、持久化、正向布局或设备结果。可选测试没有显式导出时明确 skip；当前离线来源及边界见[台账2.54](iQOO16专项实施与验收-20261023.md#254-档案ui接链读取拒绝与phase708离线检查点)。

### 共享错误恢复与 Android 整轮消费

公共 [General.jsonc](../resource/base/pipeline/General.jsonc) 的 `返回主菜单_err` 经 [ScopedRecovery](../agent/action/basics/ScopedRecovery.py) 处理，保留 Default 错误入口，恢复节点的 `next`／`on_error` 为空。处理器始终返回 `success=False`；已在可信首页时零输入。只有真实 `指挥局` entry、完整且可证明尚未尝试业务的导航历史、同帧公会页面和原返回模板全部成立时，才允许最多一次返回点击，随后仅观察。模板必须为 `指挥局/返回.png` 或其唯一单元素列表，固定 ROI 本身不足以证明按钮身份。业务节点出现、未知页面、坏图、停止、上下文漂移或预算不足时拒绝导航；不通过奖励、购买、通用确定、退出存档或 StopApp 扩大恢复范围。

Python `post_stop()`、Custom 返回值或 Maa 任务 Succeeded 均不足以证明整轮已停止。Android 的 [canonical recovery patch](../.github/android/maafwapp_recovery_patches.py) 在实际 `MaaRunner` 的 Wait 返回后、success 计数及下一次 PostTask 前，同步使用 [TaskRecoveryHistory](../.github/android/overlays/app/src/main/java/com/aliothmoon/maafw/maa/TaskRecoveryHistory.kt) 查询当前 taskId 的完整稳定历史；出现 `返回主菜单_err` 即保留原任务失败并停止本轮派发，查询不完整或 owner 改变同样拒绝继续。已命名 `completed=false` 是可保留的失败数据，不单独当作历史缺失；普通稳定失败仍沿用既有消费语义，用户 Stop 保留取消语义。两个 JNA 查询遵守固定 MaaFramework 5.14.2 的 MaaSize／ID 64 位与 MaaBool 8 位定义，不能随 Android 指针宽度改成 NativeLong。

恢复中止后，仅在实际 native Running 归零时解除 busy 和通知结束；中断或未知观测不等于已停止。该闸只覆盖共享恢复路径。ScopedRecovery 的 cleanup 只证明本处理器持有作业的收尾，不能证明原失败动作的物理触点已释放，也不替代一般异步 Stop 验收。同步 SDK 调用仍不能硬取消。回归入口为 [Python 单测](../agent/tests/test_scoped_recovery.py)、[native 内存链](../agent/tests/test_scoped_recovery_native.py)、[Android patch 测试](../.github/android/tests/test_recovery_patch.py)及 [JVM helper 测试](../.github/android/overlays/app/src/test/java/com/aliothmoon/maafw/maa/TaskRecoveryHistoryTest.kt)；Android 远程 Agent、两 ABI、新 APK 和实际游戏恢复须另验，当前证据见[专项台账 2.51](iQOO16专项实施与验收-20261023.md#251-共享恢复源码修复及首次相采样拒绝)。

## 3. 契约与约束的检查位置

下表说明硬约束的来源和适用范围；实现风格、优化建议和已知欠缺另列，不将全部发现转为禁令。

| 约束与来源 | 违规例子及正确位置 | 检查路径与边界 |
|---|---|---|
| 任务、选项和 Pipeline 引用必须匹配；来源：`interface.json` 导入与实际节点消费 | 只重命名入口节点，遗漏 `tasks/` 的 entry、`options/` 的 override 或平台/语言同名覆盖 | 全仓定向检索、maa-checker、Schema；最后在受影响组合运行任务 |
| Python Custom 名称必须可解析；来源：`agent/agent_file.py` 注册 | Pipeline 填入未注册名称；应注册实际动作/识别，角色类则走 `role_factory` | 检查注册与节点引用，针对性 pytest、资源加载和启动器运行；Schema 不能证明 Python 运行成功 |
| `cls_name` 与类名、角色配置一致；来源：`LoadSetting.py`、`role_factory.py` | 角色类拼写错误导致未选中预期策略；在 `roles/` 与配置联动 | `test_validate_config.py`、角色检测测试；实际角色进战确认 |
| 中止/空扫描不能覆盖有效缓存；来源：`RoleSelection.py` 的写入边界 | 停止后保存部分结果，或零结果仍更新刷新时间 | `test_role_scan_failure.py`、`test_role_cache_policy.py`；设备刷新与中止再验收 |
| 多个全局选项不得互相吞掉；来源：CacheRole attach 读取和选项组合契约 | 将两个选项都改写到同一个完整 JSON 字符串 | `test_cache_option_channel.py`，并检查启动器选项组合 |
| 平台与语言覆盖必须兼容共同消费者；来源：资源组和控制器附加路径 | 只验证 base，忽略 Win32 按键或英语 OCR | 检索同名节点、按矩阵做 Schema/加载/游戏验证；几何测试不能证明 OCR |
| 停止与清理必须覆盖新增循环/持有状态；来源：Tasker 停止状态和 `combat_once` 生命周期 | 新增长循环不检查停止，或会话结束后保留脏状态 | 会话、切人等相关 pytest，加启动/停止/再次运行的设备验证 |
| Fork、编码及交付约束 | 按 [AGENTS.md](../AGENTS.md) 执行，不在此重复维护 | Git 状态/diff、编码检查、精确审查提交范围；不能以忽略目录为由提交缓存或秘密 |

默认约定是沿用相邻模块和公共封装。建议优先使用识别状态驱动动作、复用现有测试替身、保留窄范围 diff；它们不要求所有小改动都召开架构评审。

### 启动、调试与构建

本地游戏验证使用 [MFW-PyQt6](https://github.com/overflow65537/MFW-PyQt6/releases) 加载仓库 `interface.json`，选择实际控制器与资源组，由启动器启动 agent。记录游戏版本、语言、控制器、识别画面尺寸、相关选项、任务入口和结果；日志定位按 [日志分析指南](../.cursor/skills/maa-punish-log-analysis/SKILL.md)。控制器可能发起真实输入，不能把运行任务当成只读探测。

桌面资源组装命令：

```powershell
& $py tools/ci/install.py
```

[install.py](../tools/ci/install.py) 将源码复制合并到固定 `install/`，可选位置参数为版本号；它会覆盖同名文件、保留未被本次覆盖的遗留文件，并修改安装副本的版本/资源 hash。需要可复现打包时先核对输出目录状态，使用隔离工作区或明确管理旧产物；不自动删除用户已有目录。它不提供完整启动器，完整桌面打包见 [install.yml](../.github/workflows/install.yml)。

Android 使用该工作流的独立 MaaFwApp 构建链，配方在 [pi-profile.yaml](../.github/android/pi-profile.yaml)，上游适配在 [patch_maafwapp.py](../.github/android/patch_maafwapp.py)。当前 Android 构建 job 的主机 Python 为 3.13，与 agent 测试/桌面打包的 3.12 分开；设备双 ABI Python 运行时由 MaaFwApp 的构建脚本独立组装，不从主机版本推定。还应核对工作流的 JDK、SDK、NDK、上游版本和签名输入；桌面 `install/` 组装成功不代表 Android 打包成功，更不代表 APK 可安装或游戏可运行。

`mine` 分支命中工作流路径过滤的推送，或手动选择 `mine` 运行 `install`，会在 Android 构建成功后发布 `mine-*` APK 预发布版本；从对应 Release 的 Assets 下载 `.apk`。预发布 job 仅依赖版本信息与 Android 构建，并单独申请 `contents: write` 权限。仅文档变更不会自动构建；正式版本标签仍由原有多平台发布链处理。

本 fork 的 `mine` Android APK 为共存专版：包名 `com.overflow65537.maafw.punish.iqoo16`，名称 `MAA Punish iqoo16`，与官方版保持独立数据和权限，不能卸载官方来迁移。配方复用 MaaFwApp 已有的点分 `app.id` 和环境占位符，只在本 fork 的 `mine` CI 注入专版身份；namespace/Kotlin 包及其他分支/正式标签的原身份保持原样。支持的配置沿用应用原有导出/导入及项目校验。

专版 launcher 图标由同一条件的 `MAA_PUNISH_APP_ICON` 选择 [.github/android/icons/logo-iqoo16.png](../.github/android/icons/logo-iqoo16.png)，配方未设置该变量时仍使用根目录 `logo.png`。MaaFwApp 原生生成图标资源并供 launcher、round icon 和 splash 使用；资源只影响 Android 专版，桌面及 PI 的原图引用保持不变。

专版首页只显示“iQOO 16 适配版”，默认、读盘、写入及导入旧 `STABLE`/`BETA`、源和 CDK 都归一化到专版策略，服务层再次强制路由静态客户端。它只读 `/iqoo16/standalone/latest.json`，下载本 fork 的 `MPA-android-iqoo16-vX.Y.Z-iqoo.<提交数>.apk`，失败不向 REST API 或 MirrorChyan 回退。`mine` 的 `BUILD_VERSION_NAME` 显式设置为同一版本（去 `mine-`/`v`），版本码仍取提交数；CI 同时校验 APK metadata、实物 badging 的包名/版名/版本码/应用名称和发布证书，并在打包前执行原更新器与专版 Kotlin 回归。AGP 9.2.1 默认只启用 Debug 单元测试，CI 在该次测试命令传入 `-Pandroid.onlyEnableUnitTestForTheTestedBuildType=false`，使所选签名 variant 的测试任务可用，不修改上游全局配置。

Pages job 仅在本 fork 的 `mine` APK 发布成功后运行，以内置 `GH_TOKEN` 认证查询 Release 元数据；它单独申请 Pages/OIDC 权限，`github-pages` 环境需允许 `mine`。同 tag 资产不覆盖，部署串行并分别校验两条清单的最高版本与上一清单；`/iqoo16/latest.json` 只接收历史原包文件名，保留已发布旧包，整个站点同时包含新旧两份 JSON，不能使旧客户端收到独立包。静态协议、设置、迁移与设备验收边界见 [iQOO 16 更新设计](plans/2026-10-20-iqoo16-update-channel-design.md)。本地补丁/版本/双清单回归使用 `& $py -m unittest discover -s .github/android/tests -v`。

重建 Pages 时从最新 `mine` 执行 `workflow_dispatch`，不要重跑迁移前只部署单份清单的历史 run；历史工作流保留当时的部署代码，可能移除新端点。首次发布独立版前应确认没有旧 Pages job 进行中或排队。

fork 不一定拥有官方 `vX.Y.Z` 标签。`mine` 的 meta 和 Android job 均在完整 checkout 后显式从官方仓库获取 `v*` 标签，不使用强制覆盖；两个入口随后按同一规则选取 `HEAD` 可达的最高正式版本，标签冲突或没有可达正式基线时失败。仅 `fetch-depth: 0` 不能保证 fork 已同步这些标签。

生成工具不是校验工具：[gen_resource_hash.py](../tools/ci/gen_resource_hash.py) 默认会改源码 `interface.json`，其他 `tools/gen_*` 和格式化工具也可能覆盖资源。只在任务需要时执行，先读参数与输出位置，再审查生成 diff。Schema 由 [sync_schema_files.yml](../.github/workflows/sync_schema_files.yml) 同步，修改或升级时关注依赖版本与消费者兼容性。

### 项目级真机设备策略

这是用户明确的**项目级持续要求**，适用于本项目所有宿主、所有agent、跨对话的真机／ADB任务及目标设备空闲期，不限某个goal、case或USB lease。纯离线且没有连接目标设备的工作照常推进；一旦连接本项目目标真机，所有任务都执行本节。仅作用于已确认的本项目目标设备，不扩展到其他项目或无关手机；同一设备仍只有一个输入执行者，其余agent读取交接证据。

每轮设备调试首次操作前，由唯一设备执行者按下列顺序落实并保留实证；后续每次重连或新设备scope重核，失效时依持续授权正常重设，不重复请求已有范围的许可：

1. 确认目标设备与当前OS／电源状态，先记录其原始自动熄屏超时、自动亮度模式、亮度和供电保持唤醒设置。原值、实际设备身份及收据仅存本轮ignored证据，交接时保留位置；跨对话沿用未结束调试的原值，不将已修改值重记为原值，也不把某台设备的具体数值固化为项目默认。
2. 使用正常系统接口 `svc power stayon true`，并读回 `stay_on_while_plugged_in` 及 `dumpsys power` 的实际mStayOn／Awake状态。只有写命令退出码或一个设置值不算生效；供电持续唤醒不等于系统超时已改为“永不”。
3. 关闭自动亮度，并将亮度调到该设备实际可用的最低值，核实际模式、亮度读回与可见系统UI。direct settings写入无效时，使用正常可见系统设置关闭自动亮度／滑条调最低并再次实读，不把静默成功当作已落实。
4. 优先使用现成“任务页→快捷选项→快捷操作→熄屏挂机”的Manual owner。它无需task或helper lease；通过实际黑罩、系统未锁及保持唤醒核验，不因lease状态inactive否定Manual。必要UI操作时临时横滑退出，完成立即恢复；空闲阶段保持。新USB lease首次建立后，先等同一session的 `screen_saver_status` 处理到active，再按当时实际解锁条正常横向拖动并等待动画，确认黑罩确已退出；同一lease已获active且正常dismiss后，USB owner被抑制，后续重入不得重复要求active，可关联原ACK与当前session／host／owner证明同一租约，Manual黑罩实际状态另行核验；解锁条会漂移，不复用固定y。当前单次正常dismiss清空所有owner，不把双owner写成必须滑动两次；helper active不等于屏保已消费新lease，不凭重复滑动推断未退出的成因。Manual归属源码见 [ScreenSaverOwnership](../.github/android/overlays/app/src/main/java/com/aliothmoon/maafw/devsession/ScreenSaverOwnership.kt)，保持边界包含助手进程存活与运行模式；进程重建或模式变化后须重新核实。黑罩的KEEP_SCREEN_ON／低窗口亮度是保持运行的遮罩，不能称物理关屏；Manual入口实际不可用时明确记录，继续维持已实证防锁和最低亮度，不另建保活daemon。

**不得因assistant final、等待、turn／对话切换、单案完成或helper／lease关闭恢复设置。** 只有用户明确结束该设备调试，或整体目标完成并执行最终收尾时，才关闭本轮遮罩并按已保存原值恢复；下次进入本项目设备调试自动重新应用本节。跨agent／跨对话交接必须传递原值／收据位置、实际生效状态与恢复责任，不能以空闲或脱离某个case推定调试已结束。

只使用已有授权范围内正常API／可见UI，不移除PIN或生物识别、不代填凭据、不绕过系统认证。沿用既有工具与输入边界，不新增Hook、MCP、全局规则、守护进程或臆造CLI参数。USB会话自身能力与本节agent执行义务分别核验，不能以helper启动或lease存在宣称系统防锁／最低亮度已生效。

一次实际实现与限制见[专项台账2.59](iQOO16专项实施与验收-20261023.md#259-本会话持续设备policy与manual黑罩已生效)，其当时设备值和进程状态只是历史证据。本节为唯一操作规范，[AGENTS.md](../AGENTS.md)只保留短硬规则入口；文件落地不等于所有宿主新会话已加载，宿主发现与执行仍须另验。

### USB 开发会话与源码同步

本能力在 `mine` 实施，首次需要集中安装包含手机端会话、屏保和重载能力的新 APK；实施及真机证据见 [2026-10-23 验收记录](USB调试会话验收-20261023.md)。尚未完成的设备项不能根据下面的命令或单元测试推定通过。

[android_debug.py](../tools/android_debug.py) 使用 Python 3.12 标准库和已有 ADB。`session` 在终端运行，不注册电脑登录自启。只有单台已授权 USB 手机与显式 `--serial` 一致才接受操作；无线 ADB、模拟器、多 USB 设备均拒绝。打开 MAA 后才开始手机会话；后台只能维持已建立的租约。

```powershell
$py = (Resolve-Path './build-debug/venv/Scripts/python.exe').Path
$adbPath = 'E:/Android_Studio_SDK/platform-tools/adb.exe' # 按本机实际路径调整
& $adbPath devices -l
$deviceSerial = '<确认后的手机 USB 序列号>'
$targetPackage = 'com.overflow65537.maafw.punish.iqoo16'
$debugArgs = @('--adb', $adbPath, '--serial', $deviceSerial, '--package', $targetPackage)

# 终端一持续运行；随后打开手机 MAA。Ctrl+C 结束会话。
& $py tools/android_debug.py @debugArgs session
# 终端二使用同一组参数；session 终端须继续运行。
& $py tools/android_debug.py @debugArgs status
& $py tools/android_debug.py @debugArgs sync
& $py tools/android_debug.py @debugArgs status --reload
& $py tools/android_debug.py @debugArgs close
```

USB会话工具本身使用现有屏保窗口的最低亮度与保持亮屏能力，不修改系统亮度、自动亮度或锁屏超时；项目agent仍必须在工具外执行[项目级真机设备策略](#项目级真机设备策略)并核实系统防锁／亮度，不以lease替代。工具不绕过系统解锁。运行模式、悬浮窗权限和前台服务失败会反馈状态。USB、手动、任务分别持有屏保使用权；拔线或心跳超时只释放 USB 使用权。右滑退出抑制当前 USB 会话的自动盖屏，保持心跳不会马上重新盖屏；重开一条会话或明确的新触发才重新申请。

`sync` 仅暂存 [共享白名单](../.github/android/overlays/app/src/main/assets/dev-source-policy.json) 内的源码：`interface.json`、任务/选项/翻译 JSON、Android 资源的 Pipeline/图片以及纯 Python。配置、日志、截图、角色缓存、模型、解释器、native/runtime、测试与桌面平台资源不进入同步。新增 Python 依赖、Kotlin/Manifest 或运行时修改仍须打包；APK 升级后须打开 MAA 完成当前 PI 安装并重建会话，工具核对 `pi.version` 后以新基线重新同步，不沿用旧版本删除清单。旧事务恢复未完成时保持阻塞。

首次安装需要集中更新一次 APK，以交付手机端能力；此后的白名单源码修改通过 `sync` 验证，无需重复安装 APK。本工具使用 Python 3.12 标准库，Android 沿用项目既有依赖，没有增加新的运行时依赖；新增依赖仍属于重新打包的范围。

**同步前置条件**：当前配置至少有一个已启用且可执行的安全任务，特权服务已通过正常运行链成功 prepare 过一次，保存了可信的运行 payload、Controller 和显示环境。空配置或刚启动、尚未 prepare 的服务会明确拒绝同步，不自动创建临时配置或启动游戏。首次可经 MAA 正常入口短跑一次经过确认的安全任务，例如 `Screencap` 短任务，再手动停止并等待收尾完成。完整启动链仍会处理运行模式、虚拟屏、分辨率及相关环境；截图 Pipeline 的名字不能证明它绝不启动应用或产生输入。服务重启或显示环境改变后，应重新确认这些前提。

注意截图缓存：MaaFramework v5.14.2 的内建 `Screencap` action [优先读取 `cached_image()`，仅缓存为空时才截图](https://github.com/MaaXYZ/MaaFramework/blob/v5.14.2/source/MaaFramework/Task/Component/Actuator.cpp#L573)。因此短跑可用于 prepare，`DirectHit` 循环反复保存同一缓存不能证明取得了新帧；首次黑缓存也不能据此归因于 Controller。需要新帧时，使用已注册的 [ScreenShot Custom action](../agent/action/basics/ScreenShot.py)（显式 `post_screencap()`），或实际图像识别路径，并核对识别结果。App 手动截图可用于制作模板，但不作为 Controller 实际识别成功的证据。

首次同步上传白名单源码，之后按手机已提交清单计算增量；删除仅限此前由工具管理的源码路径。电脑对实际内容计算 revision，包含未提交修改；APK versionCode 与源码 revision 是两种不同版本。上传只写会话专属暂存区，手机确认安全停止原生任务后才晋升，加载新 Resource 并完成新 Agent 握手后才报告 `loaded`。CLI 还核对 generation 与手机提交清单，ADB push 成功或项目解析成功都不算同步成功。

重载保留既有 Controller/虚拟显示，不主动运行 StartApp 或任何任务。首次尚未建立显示环境、显示参数变化或安全停止失败时，应明确失败，不能声称保留当前游戏页面。同步完成后从适合当前页面的入口显式验证；游戏本身并未被暂停。超时或断连后先检查 `status --reload`：手机在晋升后会自行提交或回滚，电脑退出不能强行中止该安全收敛过程。

常见错误码按实际返回排查，不通过清空配置或反复重装掩盖原因：

读取ADB exec-out输出须先验证预期载荷格式和内容，不能仅凭rc0或相同错误正文hash认定文件读取成功；release私有配置沿用现成原生export核验。

| 错误码 | 排查与下一步 |
| --- | --- |
| `display_not_previously_prepared` | 当前服务没有可信的已准备环境。按上述步骤正常短跑安全任务、停止并等待收尾，再同步。 |
| `active_configuration_requires_enabled_task` | 当前配置没有可执行的启用任务。启用一个适合当前页面的安全任务；工具不会生成临时“空配置”。 |
| `active_configuration_invalid`、`candidate_project_invalid` | 检查任务入口、选项与候选源码的项目解析结果，修正后重试；保留现有配置和回退结果。 |
| `controller_definition_changed`、`environment_changed`、`display_environment_changed` | 控制器或显示环境与先前 prepare 的内容不一致。此次保留页面重载被拒绝；明确重新建立运行环境后再验证，不承诺原页面不变。 |
| `source_state_apk_mismatch`、`manifest_apk_mismatch` | 核对目标包、APK versionCode 与 `pi.version`，完成升级后的 PI 安装并重建会话；旧事务恢复未完成时先处理恢复状态。 |
| `source_file_size_mismatch` | 同时核staged文件、当前PI实物与已提交source-state，不直接归因于传输。已授权同版本PI重解后可能出现旧追踪清单与新实物错位，按下述条件诊断，不一律删除state。 |
| `source_sync_cancelled_or_disconnected` | 同步期间会话结束或被取消。晋升前应无源码替换；晋升后先读维护状态，等待手机提交或回滚，不强行终止恢复。 |

同versionCode重新安装PI后，旧source-state可能仍有效于版本检查，却不再对应实物。只有证明已授权基线变更、实际白名单文件全量path／size／SHA匹配正确目标、旧state确已过时、无pending journal且原操作已收尾，才可在保留原件和元数据后使旧追踪状态失效，再走现成首次完整导入；继续执行stage／备份／journal及native停止／prepare／Controller校验，并以实际`loaded`／revision／generation验收。状态或归属未知时先诊断，不降低校验、不伪造state；磁盘无journal不证明进程内inflight为空。APK version变化已有自动失效逻辑，无需每次手动归档。实例见[专项台账2.62](iQOO16专项实施与验收-20261023.md#262-旧追踪清单错位诊断与706加载基线重建)。

相关最小检查：

```powershell
& $py -m unittest discover -s tools/tests -p test_android_debug.py -v
& $py -m unittest discover -s .github/android/tests -v
& $py tools/ci/check_android_pi_profile.py
```

Android CI 显式运行 `com.aliothmoon.maafw.devsession.*` 与相关 `EnvironmentHooksTest`；本地使用 fresh 固定版本应用补丁，不把旧 generated 树直接当最终交付证据。无任务防休眠、拔线恢复、三类源码真实生效及故障恢复仍需按验收记录逐项在手机观察。

同一[Android CI](../.github/workflows/install.yml)还显式运行`TaskRecoveryHistoryTest`、`MaaRunnerRecoveryHistoryTest`、`RunLogRecorderRecoveryTest`、`RunLogRecorderTest`和`RunLogComposerTest`，并在release上传前检查实际APK中Long／Int／ByteByReference的public无参构造。新增反射构造类型须精确保留真实构造；JVM通过不能替代R8后的实际DEX验包，工具缺失或检查失败不能跳过。

后续停止观察还增加`MaaFrameworkRecoveryResultLogTest`为第六个相关suite；其本地JVM通过仅证明模拟链路，新字段须随新release另验，不能回借给未包含该增量的已安装APK。

## 5. 按变更风险选择验证

| 变更 | 最小定位与相关检查 | 额外验收 |
|---|---|---|
| 文档、小范围文案 | 检查路径、链接、实际配置与 diff；i18n 文案改动检查键引用 | 涉及界面展示时看实际目标语言；纯文档不必全量测试或打包 |
| 任务、选项、OCR/模板/ROI | 顺着 tasks/options 到具体节点和平台/语言覆盖；maa-checker、相关 Schema、资源加载；已有几何回归可继续使用 | 用实际截图与设备复现成功、未命中、超时/恢复；记录游戏及资源组合 |
| Python Custom、缓存、扫描 | 注册名/参数共同消费者；选取 `test_cache_option_channel.py`、`test_role_cache_policy.py`、`test_role_scan_failure.py` 等相关测试 | 真实刷新成功、中止、零结果与旧缓存保留；需要时验证启动器选项组合 |
| 角色打法或公共战斗状态 | 角色配置/工厂、公共动作与平台节点；`test_validate_config.py`、`test_role_detect.py`、`test_refresh_field_role.py`、`test_switch.py`、`test_session_*` 中相关测试 | 实际角色与队伍进战、切人、停止、退出后再次启动；公共修改扩大到共同消费者 |
| 打包、依赖、平台适配 | 对应 CI、资源组装脚本、Android 配方检查；Python 依赖变更运行 agent 测试并核对实际框架版本 | 对应平台打包、启动/安装、资源与 agent 连通、真实任务；签名兼容单独确认 |

先执行能覆盖修改风险的目标检查，公共状态变更再扩展回归范围。现有有效强制检查仍适用；没有新增风险或失败时，不为形式重复全量测试、多角色评审和文档更新。

CI 有路径过滤，见 [agent_test.yml](../.github/workflows/agent_test.yml) 与 [check.yml](../.github/workflows/check.yml)。例如只改 `requirements.txt` 不在当前 agent 测试工作流的路径触发列表中；不得把“没有触发”当作“已通过”，本地按实际依赖影响选择测试。

## 6. 接手、交付与维护

正常工作顺序是：确认目标与工作区 → 定位入口和消费者 → 判断影响 → 修改 → 执行相关检查 → 交付证据。小任务只需简短说明；跨模块或高风险任务先列影响和验证计划。并行协作时明确文件 ownership，最终集成人审查整个 diff，保留他人改动。

交付将结果分为 **已运行通过、已运行失败、受环境阻塞、尚未执行**。分别说明静态检查、模拟测试、资源组装/打包、宿主发现和真实设备结果。确认 Custom 返回成功、框架加载成功或生成 APK，只能陈述各自证明的事实。

跨会话时在当前任务记录或交接消息中保留以下内容；没有现成任务文档且确实需要长期恢复时，再新增一份短记录：

```text
目标与完成条件：
分支 / HEAD / 工作区已有改动：
影响的平台、语言、共同消费者：
已完成修改与文件：
已运行命令、解释器/工具版本、退出码与结果：
未执行 / 阻塞及其影响：
未解决假设或风险：
下一步、所需证据、交接后的文件 ownership：
```

目录、关键运行链路、共享契约或命令变化时更新本文对应部分；战斗细节维护在战斗指南，Pipeline/日志流程维护在既有 skill，入口只保留路由与关键约束。重复出现的错误先判断是缺少上下文、实际代码缺陷还是检查缺口，再选最小修复；不默认新增 hook、MCP、全局规则或调度平台。

当前需要持续关注的边界：英语资源仍有 README 明示的未完成场景；PlayCover 缺少真实验收；Schema 与运行依赖、最新检查器可能产生版本漂移；现有测试主要是模拟对象，不能覆盖游戏画面与控制器差异。它们是现状和验证债务，不是可以降低验收标准的理由。
