# 自动战斗框架开发指南（agent）

本文档面向在本仓库内开发/扩展**自动战斗**的脚本作者。当前框架位于 `agent/action/combat/`，由三部分构成：

- **框架层（动作与识别）**：`agent/action/combat/actions/CombatActions.py`
- **配置层（角色注册）**：`agent/action/combat/config/LoadSetting.py`（`ROLE_ACTIONS`）
- **业务层（角色状态机）**：`agent/action/combat/roles/*.py`（继承 `BaseRole`）

战斗循环由 **`CombatRunner`**（`agent/action/combat/entry/runner.py`）统一驱动，Pipeline 只需调用一次 `custom_action: "CombatRunner"`。新角色**无需**在 `agent_file.py` 里逐个注册，只要 `cls_name` 与类名一致，`role_factory` 会自动扫描 `roles/` 包。

---

## 1. 运行机制概览

```
Pipeline（CombatRunner）
  → CombatTask.combat_once()
    → 进战识别队伍 / attack_template 校正 cls
    → 循环：当前角色 role.perform() → do_perform()
      → CombatActions（攻击/消球/识别/QTE）
      → request_role_switch() 切人
```

每个 tick，`BaseRole.perform()` 先处理切人阶段；非切人阶段都会通过 `refresh_field_role()` 核对站场角色，并非只在 idle 阶段校验，再进入子类的 `do_perform()`。业务逻辑本质是：**按优先级判断状态 → 调用动作节点 → 必要时切人**。该边界由 `agent/tests/test_refresh_field_role.py` 覆盖。

## 3. 新增角色：LoadSetting

在 `ROLE_ACTIONS` 中新增一项，**`cls_name` 必须与 `roles/` 下类名完全一致**。

### 3.1 常用字段

- **键名**（如 `"神威·不落日"`）：正式名称，选人/OCR 用
- **`name`**：简称别名
- **`type`**：`Attacker` / `Tank` / `Support`（破甲算 `Tank`，增幅算 `Support`）
- **`cls_name`**：如 `"Aeternion"`
- **`metadata`**：元素与代数，如 `{"fire": 100, "generation": 3}`
- **`template`**：编队头像模板列表
- **`attack_template`**：战斗内攻击键模板（可多个，用于 p1/p2 识别）
- **`skill_template`**（可选）：三色球模板，供 `Arrange_Signal_Balls()` 三消决策

### 3.2 示例

```python
"神威·不落日": {
    "name": "不落日",
    "type": "Tank",
    "cls_name": "Aeternion",
    "metadata": {"fire": 100, "generation": 3},
    "template": [
        "人物索引/神威/不落日/不落日.png",
        "人物索引/神威/不落日/不落日_终解.png",
    ],
    "attack_template": [
        "自定义战斗/神威/不落日/不落日.png",
        "自定义战斗/神威/不落日/不落日_释能.png",
    ],
},
```

## 4. 新增角色：roles 业务脚本

### 4.1 约定

- 文件：`agent/action/combat/roles/aeternion.py`
- 类名：`class Aeternion(BaseRole)`（与 `cls_name` 一致）
- 入口：实现 `do_perform()`，用 `self.phase` 做状态机
- 切人：`self.combat.request_role_switch(self)`（由 `CombatTask` 统一处理 QTE）
- 动作：`self.action.*`（`CombatActions` 实例）

### 4.2 最小模板

```python
from action.combat.core.role import BaseRole


class YourRole(BaseRole):
    def do_perform(self) -> None:
        if self.combat.context.tasker.stopping:
            return

        if self.phase == "idle":
            self.action.lens_lock()
            self.phase = "combat"
            return

        if self.action.check_Skill_energy_bar():
            self.action.use_skill_until_empty()
            self.action.use_qte()
            self.combat.request_role_switch(self)
            return

        self.action.continuous_attack(8, 50)

    def on_switch_failed(self) -> None:
        self.phase = "combat"
```

### 4.3 编写建议

- **状态机写在模块 docstring**，便于 LLM/他人阅读（参考 `arete.py`、`aeternion.py`）
- **补攻有阶段边界**：仅在允许普通攻击的常态步骤使用 `_run_step` 或前后补攻；不要对消球、长按和等待统一添加输入。`attack()` 本身还会判断自动闪避，不能把它当成纯普攻或无副作用保活。
- **异常只收尾释放**：步骤正文抛出异常时不继续尾部攻击；不要把尾攻放入 `finally`。`finally` 保留触点释放和状态清理，不能因清理而追加攻击、闪避或 QTE。当前 Aeternion、Arete、Dirge、Lacrimosa 的 `_run_step` 只在正文正常返回后补攻；这项修复不等于停止、受保护阶段或 QTE 合同已全部落地。
- **识别优先**：条件判断走 `check_status("节点名")`，节点定义在 `Check_Characters_Skill/<Cls>.jsonc`
- **双形态**：现有攻击键识别常用 ROI `[1113, 556, 138, 142]`；是否可跨平台复用，以实际截图、按钮布局和已有覆盖为准
- **切人与站场**：已有轮切角色常用 `use_skill_until_empty()` → `use_qte()` → `request_role_switch()`；这不是所有角色的大招后默认流程。默认留场的策略须明确大招终态与后续循环，不能沿用该顺序自动切人。

### 4.4 受保护阶段与后续站场合同

逆冕的机制、默认站场顺序、信号和本场能力要求集中维护在[逆冕站场策略](逆冕站场策略.md)；专项真实验收进度继续记录在带日期台账。

特殊球持有、必要长普结算、蓄力大招和斩切等受保护阶段，不允许为了“防发呆”插入保活攻击或闪避。角色校验、等待回调和退战检查也须遵守这一边界：不得经 `_blind_attack_tick`、`on_tick` 或公共辅助函数间接输入。

当前显式启用的逆冕专项已有纯观察路径和 [CombatInputScope](../agent/action/combat/input_control.py) 持有、点按基础；完整状态机与站场安全 QTE 尚未就绪，仍以 `strategy_not_ready` 在输入前拒绝。普通模式沿用原有角色校验、攻击及轮切行为。维护这些基础能力时遵守以下合同：

- **纯观察**：专项通过 `is_observation_protected()` 禁用盲攻/等待攻击回调，`observe_hold_state(image)` 只消费作用域提供的当前有效帧；角色观察回调同样不得攻击、闪避、QTE或自行采图。普通模式的角色校验仍可能带输入；只在角色脚本中删去 `attack()` 不足以取得专项观察语义。
- **ready QTE**：新帧确认成员和 ready 后才请求，旧帧或持续 ready 同一窗口不重复点击，联动后重新采图。现有 `use_qte()` 依次点击 `qte1`、`qte2`，不检查 ready、成员或站场，因此不能用于证明“不切人”。[qte_release.py](../agent/action/combat/qte_release.py) 已有 ready 识别与点击入口，但尚不具备上述完整会话、窗口去重与持有期触点约束。
- **持有与停止**：专项 `CombatInputScope` 已登记主触点归属、单调期限、停止/观察与 `finally` 释放；无法确认Job或释放终态时保留未确认状态。持有期采图经 [capture.py](../agent/action/combat/capture.py) 的作用域路径执行。普通down/up和 `long_press_dodge_until()` 不自动取得这些保证；双触点、异常释放及停止后重启仍须目标控制器验收，不新增线程争抢输入。
- **单次点按**：专项 `tap_primary_input()` 经共享退战观察调用 `tap_semantic()`；同一Controller的Down成功终态后立即Up，不主动等待、不在按下期间采图，也不调用普通攻击附带的自动闪避。调用方以 `start_deadline` 传入有限绝对开始期限；逆冕取本帧完成时间加1秒与prepare期限的较早值。Scope在目标解析、Controller获取、调用方守卫及最后同步停止查询之后，以本地单调时钟再次拒绝超期开始；不能用重复观察追加同步查询来代替此检查。通用API的None仅兼容无此时限的调用，逆冕补攻必须传值。该检查约束主机发请求前的时点，不保证原生调用或物理按压的时长；迟到Down、停止和Up未确认仍保留责任。
- **基础补刃意**：必要结算、大招和已激活特殊球优先。仅当结算、深渊相、斩切相、特殊球激活和大招ready五项均明确NO，同帧正HP、身份入口、scope及期限有效时，一轮点按一次攻击；UNKNOWN继续观察。输入后必须新采图，连续补攻及外部reset不刷新prepare预算。黄球组和槽位未就绪时不补黄消；实现与设备边界见[补资源设计](plans/2026-10-24-iqoo16-resource-rebuild-design.md)。
- **输入坐标校验**：`hold_semantic()` 和 `tap_semantic()` 的 `position_validator=None` 默认保留既有路径；可选回调接收本次 `primary_input_position()` 解析、即将用于 Down 的不可变 `(x, y)`，必须严格返回 `True`。返回其他值或抛错均在触点登记前拒绝，不发送 Down/Up/Stop；回调只校验该坐标，不重新读取 Context 代替校验消费值，也不得自行输入。它不能替代帧龄、停止或预算检查。
- **Controller Job 生命周期**：已核实 MaaFramework **5.14.2 Agent端**重复读取 `tasker.controller` 会替换并销毁旧原生 `RemoteController`；Python Job保留包装对象不能保活该原生对象。同一操作组的Down、持有期采图、Up及尚未终态的cleanup必须复用 `scope.controller_for_jobs()` 返回的Controller。observer只消费当前帧，不得自行获取或替换Controller，包括读取 `tasker.controller.cached_image` 或调用无scope的普通采图；当前共享observer通过传入帧和识别接口工作。有未确认Job时，其他动作也不得绕过scope读取getter。全部触点、释放及采图所有权确认结束后由 `discard_idle_controller()` 丢弃引用，下一操作再取，不能永久缓存整个会话的旧Controller。升级依赖时重新核对此行为，不将本版本结论外推到所有版本。
- **原生任务终态通知**：固定 MaaFramework **5.14.2 / native_android** 会在任务终态、队列无待执行任务时提交 `inactive`；此后端的 [固定版本实现](https://github.com/MaaXYZ/MaaFramework/blob/8061d5bcaa3f07afcc1008795913663f64de46c8/source/MaaAndroidNativeControlUnit/Manager/AndroidNativeControlUnitMgr.cpp#L301) 仅返回成功，不注入触摸或关闭应用。日志 `info.force_stop=true` 是配置回读，不能计为已执行关闭。分析时区分生命周期通知与输入动作，但仍须独立核实 Up、原任务终态、绑定及无触点；不能泛允许未知动作、其他后端或版本。事后离线重放与原现场判定分别保留，不能用重放通过覆盖现场未确认。
- **能力与证据**：截图有效性和几何回归不证明帧龄、真实 OCR、触点释放或游戏结算。高级辅助方式未通过设备探针时保持关闭；不能用未验证的输入方式补救基础采图或停止失败。

专项阶段、固定任务矩阵和未验边界见 [iQOO16 专项实施与验收记录](iQOO16专项实施与验收-20261023.md)。

逆冕专项的实际 UI 入口为[战斗辅助](../tasks/战斗辅助.json)末尾的“逆冕站场专项”父开关，默认 No；[共享选项](../options/inverse_crown_profile.json)的 Yes 仅从已有战斗画面走唯一普通 `战斗中` 边，不带 JumpBack，5000ms 仅为启动识别预算，不自动选人、开战、剧情或补体力。唯一 child 将 `enabled/scene/source/rank/signature_weapon_confirmed` 五字段原子发送到调用节点 attach；No 保留兄弟关闭选择且不消费旧 child，跨任务覆盖不残留。完整输入合同见[开发指南](开发与验证指南.md#逆冕本场档案选项)。

消费者读取失败返回 None／坏类型必须以 `profile_invalid` 拒绝，不能静默转入普通战斗；合法空 dict、有效节点缺 profile 和显式 No 仍兼容。档案中的场景、阶级及专武事实不等于已实现或已验收对应机制，未知本场事实不继承账号；两处 `strategy_not_ready` 继续关闭，真实 UI／持久化、正向布局和游戏策略均须另验。

逆冕专项 `enabled=true` 时，Runner 在构造战斗会话前通过 [`inverse_crown_layout.py`](../agent/action/combat/entry/inverse_crown_layout.py) 校验当前控制器、八区及[持久 HUD 绑定](开发与验证指南.md#角色缓存与布局)，再以当前画面尺寸调用 `LoadRoiZone.apply_offsets()`。入口在同一 Context 读回攻击／特殊球／八槽、两项顶部 HUD 的精确 ROI 和零 `roi_offset`，并校验读取期间缓存字节不变；失败为 `layout_calibration_required`。技能仅在该 Context 以 ADB 默认框中心加既有平移覆盖目标，再核最终落点精确等于已识别框中心；共享资源默认值、缓存矩形和普通路径不因此改写。这不改变全局“缓存组件信息”No，也不在 HUD 画面采集按钮布局。缓存图只提供几何边界，不证明当前新帧、HUD 信号或技能接纳；正式策略仍需首张成功新帧验证，两处 `strategy_not_ready` 门保持关闭。详见 [专项基础联接](plans/2026-10-23-iqoo16-inverse-crown-foundation.md)。

逆冕专项快照另有外观字段 `resource_appearance=empty/full/unknown` 与 `skill_blue_ring=YES/UNKNOWN`，由[生产观察代码](../agent/action/combat/roles/inverse_crown.py)读取当前帧；它们不映射 `ultimate_ready`、相、必要结算、末段或终结，也不改变普通分支或解除两处策略门。当前只支持人工对照过的1280×720画面、213×3条内部与124×126技能框，几何须与真实缓存及当前Context一致；坏型、漂移、黑白图拒绝发布确定外观，近满暗尾或强特效下的资源外观保持unknown。几何wrapper在技能同步读取后做固定末尾读回，由原5次增为9次节点读取；这是有限一致性复核，不是原子快照或原生调用耗时保证，同帧正HP、帧龄、停止及预算仍沿原合同。像素规则和反例维护在[外观回归](../agent/tests/test_inverse_crown_visual.py)，不把样本阈值复制到指南。

### 4.5 结果与回调语义

`CombatTask.combat_end()` 在关闭输入作用域后、清空队伍与角色前冻结一次 `outcome`，通过现有 `LoggerComponent` 输出 `combat_result`；普通模式写既有日志，专项审计模式使用 `emit_audit()`。Runner 读取到 `last_outcome`，每次调用先清空；构造会话前的配置/布局拒绝也输出同一结构。`callback_status` 只说明回调完成、拒绝或异常，普通模式保留原 `RunResult(success=True)` 合同，不能据此判断通关。

结果分别记录 `exit_reason` 和 `cleanup_reason`，清理失败不覆盖原停止、死亡或异常原因；异常只保存类型。当前 `combat_end_condition`、`hp_zero`、外部界面等退战条件均缺少胜负正向证据，故 `game_outcome` 保持 `UNKNOWN`，不能把退战判成胜利或失败。实际角色绑定在严格校验前保存请求类、真实实现类和回退原因；同色位相同绑定去重，最多保留最近64次变化并明确累计截断数。快照不依赖已清空或重置的角色对象。针对性回归见 [test_combat_outcome.py](../agent/tests/test_combat_outcome.py)；日志/模拟通过不代表设备或任务业务终态已验收。

结果写入抛错时，内存快照以 `emission_exception_type` 保存异常类型，不向已失败的日志出口重试，也不保存异常全文；状态仍清空，但跳过该次清理末尾的结束日志，避免持续断管再次覆盖原异常。传播优先级为原战斗异常、输入清理异常、结果写入异常；已知预检拒绝仍返回 `success=False`，其他预检异常仍传播原异常。没有更早异常时，结果写入失败会令回调报错；Runner 的 `last_outcome` 保留更新后的诊断。该字段为空不代表 Android 日志已送达。

#### 矩阵循生的任务局部身份门

`tasks/矩阵循生.json` 在当前 `战斗中.attach` 中设置 `roguelike3_identity={"version":1,"require_known_field":true}`。Runner 只消费本次节点的这一严格协议，不从选人节点或历史名单推断模式，也不通过参数指定角色类。provider 在采用已发布名单前重新识别当前场上角色；旧专属名单不能绕过核验，明确识别出的通用角色仍可使用 GeneralFight，`未知 → GeneralFight` 兜底不能通过此门。

启用后，provider、初始 setup 的 `_correct_role_from_field()` 及 `refresh_field_role()` 三处角色检测只识别，不通过 `on_tick` 盲攻；未知、名单不符或实际策略实现不符即拒绝。身份拒绝保留 `REJECTED/UNKNOWN`，识别、cleanup 和结果写入异常保留 `ERROR/UNKNOWN`，均沿原 cleanup 冻结 outcome。只有该 policy 已成功启用后，Runner 才将这类拒绝或异常返回为 `success=False`，由任务局部 `on_error → 矩阵循生_身份拒绝停止` 执行 StopTask；MaaFramework 的裸 Python callback 异常并不保证自动转换为 native false。启用前的异常及其他模式仍按既有传播合同处理；`combat_once()` 进入 try 前的启动日志若自身抛错，可能尚无 frozen outcome，不能由 native False 推定结果日志已送达。StopTask 的原生 Succeeded 不能当游戏胜利。

这一保护覆盖初始战斗输入前的身份门和上述三个检测点，不是逐条输入身份作用域。已确认身份后的普通切人等待 `attacker_callback`、`_sleep_check()` 等输入窗口仍存在；R03 没有并入逆冕 observation/input scope，两处 `strategy_not_ready` 保持关闭。回归入口为 [身份门测试](../agent/tests/test_r03_identity_guard.py) 与 [真实 native 错误路由测试](../agent/tests/test_r03_identity_guard_native.py)，合成识别与本地 Controller 证据不替代真实游戏身份、HUD 或策略验收。

### 4.6 退战、错误恢复与整轮停止

战斗回调结果、退战条件与整个启动器任务轮的终止分别核验。公共错误节点 `返回主菜单_err` 由 [ScopedRecovery](../agent/action/basics/ScopedRecovery.py) 负责；对战斗、奖励、未知页及不能证明尚未尝试业务的历史，当前处理器不追加恢复导航，只请求停止并保留原业务失败。它不执行通用确认、退出存档或 StopApp，也不以恢复到首页证明通关。

Python `post_stop()` 后 stopping 可以复位，原任务也可能呈 Succeeded；Android 通过 [TaskRecoveryHistory](../.github/android/overlays/app/src/main/java/com/aliothmoon/maafw/maa/TaskRecoveryHistory.kt) 在实际 Wait 后同步核当前任务的稳定完整历史，在计成功及派发下一任务前拦截共享恢复节点或不足的查询结果。用户 Stop 的取消语义、普通已命名 `completed=false` 失败记录均保留。恢复中止后须等真实 native Running 归零才解除 busy；未知或线程中断不能提前报告结束。详细链路及测试入口见[开发指南](开发与验证指南.md#共享错误恢复与-android-整轮消费)。

这条恢复链与输入 Scope 的责任边界分别保留：handler cleanup 仅覆盖自身作业，不能证明原失败动作的物理 Up、所有活动触点或其他异步 Stop 已完成。新增持有／恢复路径仍须提供归属触点、成功释放、原任务终态和真实页面的证据；Android／远程 Agent 与实际游戏结果不能由宿主内存或 JVM 测试代替。

## 5. Pipeline 与识别节点

### 5.1 动作节点

定义于 `resource/base/pipeline/Auto_Battle/Auto_Battle_Action.jsonc`（ADB）与 `resource/pgr_win32/pipeline/Auto_Battle_action.jsonc`（Win32）：

`攻击`、`闪避`、`技能`、`长按攻击`、`长按闪避`、`消球1`~`消球8`、`qte1`、`qte2`、`锁定视角`、`辅助机` 等。

### 5.2 角色特判

每个角色可在 `Check_Characters_Skill/<ClsName>.jsonc` 增加节点，例如：

- `检查阶段p1_不落日` / `检查阶段p2_不落日`：`TemplateMatch` + 攻击键模板
- `检查p1核心条_不落日`：`ColorMatch` + ROI/HSV

业务中调用：

```python
if self.action.check_status("检查p1核心条_不落日"):
    ...
```

### 5.3 Win32 覆写

`resource/pgr_win32/pipeline/Auto_Battle/Check_Characters_Skill/` 下使用同名节点覆盖平台差异。许多节点只覆盖 ROI，其余字段复用 base；这不是所有修改都只能写 ROI 的限制。先核对实际加载组合、识别字段和键盘动作，再只覆写必要差异。核心条等 UI 需 Win32 实机标定。

## 6. CombatActions 常用 API

| 方法 | 说明 |
|------|------|
| `attack()` / `continuous_attack(n, ms)` | 普攻，调用前可能执行自动闪避；不用于受保护阶段的纯观察 |
| `dodge()` / `long_press_dodge(ms)` | 闪避（固定时长） |
| `long_press_dodge_until(node, timeout)` | 按住闪避直至识别命中（登龙充能等；同键位，可视觉松手） |
| `long_press_attack(ms)` | 长按普攻 |
| `use_skill()` / `use_skill_until_empty()` | 大招 |
| `ball_elimination_target(slot)` | 消指定位球（1~8） |
| `count_signal_balls()` | OCR 球数 |
| `Arrange_Signal_Balls("red"\|"blue"\|"yellow"\|"any")` | 三消决策（需 `skill_template`） |
| `check_Skill_energy_bar()` | 大招能量条 |
| `check_status(node)` | 跑 Pipeline 识别节点 |
| `use_qte()` | 依次点击 qte1、qte2，不识别 ready；不是站场安全 QTE |
| `auxiliary_machine()` | 辅助机 |
| `lens_lock()` | 锁定视角 |

切人请用 **`self.combat.request_role_switch(self)`**，不要直接拼 QTE 坐标。

## 8. 调试与常见问题

- **角色不生效**：检查 `cls_name` 是否与类名一致、是否继承 `BaseRole`、`LoadSetting` 是否登记
- **识别不命中**：用 `check_status(node, pipeline_override={...})` 临时调 ROI；稳定后写入 jsonc
- **Win32/ADB 差异**：模板需分平台截图；Pipeline ROI 在 `pgr_win32` 覆写
- **三消无效**：确认 `skill_template` 已配置且 `role_name` 能匹配到 `ROLE_ACTIONS`
